Computer-Use Automation System

Demo narration, decision notes and Q&A prep · interface.ai take-home · prepared 15 September 2026

The system learns a task in a legacy UI once with an LLM, records what it learned as a typed, versioned capability artifact, and then replays that artifact deterministically with no model in the loop. Anything irreversible, or anything it has not seen before, stops and hands a person the same live browser session.

This document is the running order for the walkthrough, plus the reasoning behind each design decision, so you can answer "why did you do it that way?" without hunting through code.

1 · The shape of the answer

Three things make this different from a Playwright script or from an agent that runs live every time:

DecisionWhy, and what it buys
Learn once, replay foreverA model is slow, costs money and is non-deterministic. A recorded artifact replays in about two seconds with no API call at all. The model is a compiler, not a runtime.
The artifact is a contract, not a transcriptTyped inputs and outputs, preconditions, expectations, locator fallbacks, risk flags, and a catalog of outcomes it knows how to handle. A reviewer can approve or reject it without reading a log.
Escalation is the same sessionWhen it gets stuck, a human takes over the automation's own browser — same cookies, same frames, same scroll position — and hands back mid-flow. Not a restart, not a copy.

Why a mock application rather than a real site

The interesting behaviour is what happens when things go wrong: session expiry, an undeclared dialog, a 500, a slow page, a permission refusal. Only an application you own can produce each of those on demand and repeatably. Legacy CU Core is a deliberately dated core-banking UI — framesets, table layouts, no test ids, a native confirm() at the point of no return — with synthetic data only, and a fault-injection seam the demo drives.

3 · Running order

Roughly 14 minutes. If you need to cut, shorten Act 2 and keep Acts 5, 6 and 7 whole.

Before you press record

# free the ports, or the engine dies silently behind a stale process
lsof -ti:4100,4200,4300 | xargs kill -9 2>/dev/null

pnpm cua doctor            # expect: 8 ok, 1 warning, 0 failures
pnpm demo                  # target app + engine + console, Ctrl-C stops all three

# reset the two pieces of state that drift between rehearsals
#  1. G1 must be a DRAFT, or Act 3's refusal beat does not fire
#  2. the live-learn capability must NOT exist yet
rm -f artifacts/member-branch-and-tenure@1.json

Restarting the target app resets the account numbering, so every rehearsal starts at CU-700001. Record the terminal window only — your .env holds a live API key.

Act 1 — the system being automated (60s)

Open localhost:4100, sign in as demo / demo, search 10042.

"This is the kind of core banking UI that still runs in production and that nobody is going to rewrite. Framesets, table layouts, no API, no test ids. The balance I want is in an unlabelled table cell. That constraint drives most of the design."

Act 2 — learning a task (90s)

pnpm cua discover --goal "Look up member {memberId} and read the current balance of their Savings account." --url http://localhost:4100/ --capability-id member-savings-balance --param memberId=10042

"The model never sees raw HTML. It sees an accessibility tree flattened across frames, plus a screenshot with the interactive elements numbered. {memberId} is a parameter, and the password is a reference to an environment variable — the literal value is substituted at the browser, after the model has decided, so a credential never reaches the model or the transcript."

pnpm cua artifact summary artifacts/member-savings-balance@1.json

"That is the output — not a transcript. A typed contract: inputs, outputs, every step with its locator fallbacks, what each step expects to be true afterwards, and the outcomes it knows how to handle."

Act 3 — deterministic replay, and the approval gate (90s)

pnpm cua replay artifacts/member-savings-balance@2.json --param memberId=10042 → FAILURE ARTIFACT_NOT_APPROVED, exit 2, in 3ms without opening a browser.

"A model worked this out once. That does not make it allowed to run unattended. Approval is a human decision made once, at review time, rather than on every run."

Approve it on the console's Capabilities page. Show the contract, the secrets rendered as references, and the locator fallback chain. Then replay for 10042, then for 10077.

"Two seconds, no model, no API cost, same answer every time. The second run returns a different balance from the same artifact — so the parameter is real."

Act 4 — the three kinds of wrong (2.5 min)

Run these back to back and read the exit codes aloud. This is the part that separates a demo from a toy.

pnpm cua replay …@2.json --param memberId=99999
#   BUSINESS_OUTCOME MEMBER_NOT_FOUND            exit 0

pnpm cua replay …@2.json --param memberId=10042 --fault session_expired
#   SUCCESS — recovered by re-running the login prelude   exit 0

pnpm cua replay …@2.json --param memberId=10042 --fault session_expired:sticky
#   FAILURE RECOVERY_LOOP                        exit 2

"Three different kinds of wrong. 'No such member' is an answer, not an error — the automation worked perfectly, so exit 0 and the caller gets a typed business outcome. A session expiry is recoverable, so it re-runs the login prelude and carries on, and the caller never learns it happened. The same expiry that never clears is bounded after two attempts and reported. A caller can branch on these without parsing a log."

Open evidence/replay-g1-recovery-loop/failure-*.md — the narrative names the expected state, the observed state and a suggested next action, next to a screenshot, an accessibility snapshot and the page text.

Act 5 — a human takes over the same live session (3 min)

This is the part the brief cares about most. Do it in the console.

On Start: capability member-savings-balance@2, member 10042, Pace "Watchable — a beat between steps", Break something → "Undeclared error on the next click". Press Replay.

Pace matters: at full speed the run finishes before the live viewport renders a frame, and the live view is the most convincing thing in the demo.

The engine stops by itself: UNKNOWN_DIALOG, run state paused, the viewport labelled "nobody is driving", a Waiting badge in the nav.

"It did not guess. That dialog is not in this capability's outcome catalog, so it refuses to touch it. An automation that dismisses unknown dialogs is an automation that will eventually dismiss something expensive."

Take control → state becomes human control, badge flips to "you are driving", Accept/Dismiss appear over the live frame. Dismiss the alert yourself. Then Hand back.

"Seven steps. An uninterrupted run of this capability is also seven steps — so it resumed the step it stopped at, in the session it paused in. The browser was never restarted, and the cookies and frames are the ones my own clicks left behind."

Show Waiting: resolved · replay failure · same · by operator-1.

Act 6 — teaching it something new, live (2 min)

This answers the question everyone asks: does it only do the two things you pre-built?

Ask the audience for a fact about a member, or use this one: 
pnpm cua discover \
  --goal "Look up member {memberId} and report which branch they belong to and the date they have been a member since." \
  --url http://localhost:4100/ --capability-id member-branch-and-tenure --param memberId=10042 \
  --name "Member branch and tenure"

Verified timing: 25 seconds, 8 model calls, about $0.07, producing a 4-step artifact with a login prelude and two outputs, which then replayed in 2.2s and generalised to a member it had never seen.

This goal has been rehearsed once and then deliberately deleted — the artifact and its evidence are not in the repository and never were. So the run you do on camera is genuinely the first time the system has seen this goal, and you already know it works, how long it takes and what it costs. That is the difference between a live demo and a gamble. After a rehearsal, delete it again with the rm -f in the pre-flight block above.

"I have never run that goal before. It signed in, searched, found both values in a different table from the first capability, and worked out a re-readable anchor for each — 'the cell to the right of the label Branch'. That anchor is what makes the replay deterministic."

pnpm cua replay artifacts/member-branch-and-tenure@1.json --param memberId=10042 --allow-draft → {"branch":"Main Street","memberSince":"2014-03-11"} in 2.2s.
Then --param memberId=10077 → {"branch":"Riverside","memberSince":"2018-09-30"}.

"Twenty-five seconds to learn it, two seconds to run it, and it generalises to a member it was never shown. That is the whole thesis: the expensive, non-deterministic part happens once."

Act 7 — the flow that actually commits something (3 min)

G1 reads. G2 opens an account. Show the evidence of the real run first — a live Claude run here is 40 seconds of dead air.

cat evidence/discovery-g2-open-subaccount/run.json — 15 steps, 15 calls, $0.14. Then open interventions.json: three interventions.

"It stopped three times. Two were the policy: the button whose label matches the irreversible list, and the browser's own confirm dialog — which is the step that actually opens the account. The first one the model raised itself, before any rule fired: it reached the review screen and asked for a human on its own initiative."

On Capabilities, show steps 7 and 8 of member-open-subaccount@1, both tagged risky · point of no return.

Then the closing pair — same artifact, same parameters, one policy setting different:

pnpm cua replay artifacts/member-open-subaccount@1.json --param memberId=10042
#   SUCCESS  {"confirmationNumber":"CU-700001"}  side effects: committed   exit 0

pnpm cua replay artifacts/member-open-subaccount@1.json --param memberId=10042 --risky block
#   FAILURE POLICY_VIOLATION                     side effects: none        exit 2

"Same capability, same inputs, one line of policy, and the difference is whether an account gets opened. The guardrail belongs to the deployment, not to the recorded flow."

Show the new account in the bank UI. Note the confirmation number changes every run — each run really opens one.

Act 8 — safety and evidence (90s)

pnpm cua doctor, then policy.yaml on screen.

"The secret check asks git, not .gitignore — those two disagree exactly when a file was staged before the ignore rule was written, which is the case that actually leaks a key. And deleting it later does not help, because history keeps it."

"Everything the engine may do is one validated file, loaded by every entry point. Four layers enforce it: the model's decision, the surface boundary, the network, and a pre-flight check that an artifact's policy is a subset of the global one. A human who takes control is not blocked by it — they are recorded as an override, because refusing them would disable escalation exactly when it is needed."

Finish on evidence/ — one directory per run, and say the limit out loud.

"Screenshots are not masked. They render whatever was on screen, including the member ID. The schema pins that flag to false so nobody can claim otherwise, and it is written down in the README. Everything here is synthetic."

4 · Error handling, in full

Every run ends in exactly one of four shapes, each with its own exit code. This is the single most important design decision in the project, because it is what lets a caller automate against the thing.

OutcomeExitMeaning · who acts
success0The task completed; typed outputs returned.
business_outcome0The application said no, legitimately — no such member, validation rejected, not authorised. The automation worked. A caller branches on the code; nobody is paged.
failure2The automation could not proceed. Always carries a failure bundle: narrative, screenshots, accessibility snapshot, page text.
escalated3A human is needed — a risky step, an unknown state, or a failure the caller asked to escalate rather than fail.

Recoverable conditions — handled without telling anyone

CodeWhat the engine does
SESSION_EXPIREDRe-runs the login prelude, then restarts the flow from the step it lost.
SERVER_ERRORReloads and retries, bounded.
MAINTENANCE_NOTICEDismisses a dialog that is in the outcome catalog.
SLOW_LOADTolerates it, extends the wait, and flags it in evidence as a soft signal.
RECOVERY_LOOPThe guard: the same recoverable condition twice at the same step stops the run rather than retrying forever.

Hard failures — deliberately debuggable

WRONG_SCREEN (a step's precondition does not hold) · LOCATOR_NOT_FOUND (lists every strategy tried and what was actually visible) · CHECKPOINT_FAILED (the action ran but the expected state did not appear) · UNKNOWN_DIALOG · STEP_TIMEOUT / RUN_TIMEOUT · UNSAFE_RESTART (refuses to restart a flow that already committed something).

Refused before a browser even opens

INVALID_ARTIFACT · INVALID_INPUT (a parameter fails its declared pattern) · MISSING_SECRET · ARTIFACT_NOT_APPROVED · POLICY_VIOLATION · RUN_IN_PROGRESS. Catching these pre-flight means a bad call costs milliseconds rather than a browser session, and stepsRun: 0 proves nothing touched the application.

5 · Decisions and trade-offs

Locators: many candidates, ranked, with a drift signal

Every recorded target carries a chain — accessible role + name, then a CSS path, then visual position — with the recorder's own rationale for each. On replay the engine tries them in order. If it matches on a fallback, that is not a failure: it emits a drift event, which is the early warning that the screen is changing under the artifact. XPath was rejected because it encodes exactly the structure a legacy UI redesign changes.

Preconditions are screen signatures, not URLs

In a frameset the top-level URL barely changes. Each step instead asserts a URL pattern plus N of M landmarks, so a step refuses to run on the wrong screen — the difference between a clean WRONG_SCREEN and clicking blindly into whatever happened to be there.

Session control by wrapping, not by contract

A lease could have been threaded through Surface.act. Instead LeasedSurface wraps the surface, so the perception contract stays free of control-plane concerns — and revoking a lease disarms every reference at once, including one a caller captured before an await. The policy layer is a second wrapper that composes with it.

Policy is data

One validated policy.yaml. Unknown keys are rejected rather than ignored: a misspelled security control that silently enforces nothing is worse than a startup error. One field is typed as the literal false — screenshot masking we did not build — so no deployment can turn on a feature that does not exist.

Risk has two grades

The sub-account flow posts twice: Continue validates and re-renders, Open Account moves money. Treating both as risky would ask a human to approve a step that commits nothing — and an operator who is asked to approve noise clicks through the prompt that matters at the same speed. So a plain form submit is graded sideEffect: possible and runs; only an irreversible signal escalates.

6 · Things covered beyond the brief

Ask for these by name if the interviewer wants depth — each was a real problem found by running the thing, not by planning.

The point of no return is a native dialog

The application takes its final approval with confirm(). The click fails with the dialog still open; accepting it is what opens the account. The model had no tool that could answer a dialog, so goal G2 was impossible — with the whole test suite green. Adding the tool exposed five further defects, every one of which produced a plausible wrong answer rather than a crash: the recorder dropped the commit step entirely; pointOfNoReturn was only ever set on a risky click; a modal is not a screen, so the recorded precondition could never be satisfied; the dialog matched UNKNOWN_DIALOG on the very step that exists to answer it; and replay treated the dialog-raising click as a surface error.

A monitoring signal that fired on a page that had not changed

Visual drift was intersection-over-union of the control's box against its recording. It reported drift on every control of an unchanged page — legacy buttons are ~37×14px, and IoU falls off a cliff at that scale. Replaced with centre displacement over a scale floor. Nothing failed; the finding came from reading the evidence of a passing run and asking why it had anything to report.

Three separate redaction leaks

The last one wrote interventions.json unredacted, putting a member ID in a captured URL. The fix was a test that walks every file a handover writes rather than the files someone thought of. The honest limit is stated in the README: screenshots are not masked.

Derived state, not stored

Run status was a stored field and stuck on "running" forever, because teardown fires a change callback while the state is still running. Made a getter. The general rule — if a value can be derived, derive it, especially where callbacks fire during teardown — came up four times.

Tests that modified the fixtures they were reading

Twice. Once when an artifact was approved on disk while the suite read it as a draft fixture; once when the console learned to record artifacts and the suite began overwriting a committed deliverable. Both now use isolated directories.

Smaller ones worth a sentence each

  • Prelude circularity — the sign-in screen matches SESSION_EXPIRED, and is also where the login prelude legitimately starts. That outcome is inert while checking a precondition inside its own prelude.
  • The run clock stops for humans — time parked in an intervention does not count against the run's timeout, or long handovers would fail runs that were never stuck.
  • Extraction anchors are checked for leakage — an anchor containing the member ID would be a different anchor for every member, so the recorder rejects it.
  • Dialogs raced, not awaited — a modal used to freeze Playwright mid-action; the surface now races the action against dialog appearance, with a timeout backstop.
  • Loopback only, one operator — the console binds to 127.0.0.1 and has no auth; that is stated as a cut, with approvedBy already in the record for the identity that would fix it.

7 · Questions you should expect

QuestionAnswer
"What if the UI changes?"Locator fallbacks absorb small changes and emit a drift event as early warning. A structural change fails as WRONG_SCREEN or LOCATOR_NOT_FOUND with a bundle, and re-discovery produces a new artifact version. The artifact is versioned precisely so this is a diff, not a mystery.
"Why not run the agent every time?"Cost, latency, and non-determinism. $0.07 and 25 seconds versus $0 and 2 seconds — and a compliance story you can actually make, because the replay path has no model in it.
"How do you stop it doing something dangerous?"Four enforcement layers from one policy file, an approval gate before unattended replay, and two risk grades so the escalation that matters is not buried in noise. Demonstrated by running the same artifact with one flag changed.
"How does this scale past two capabilities?"Honest answer: a catalog API and confidence/stability scoring are designed and listed as cuts, not built. The artifact schema already carries the fields they need — status, version, provenance, approvedBy.
"What would you do next?"Screenshot masking (bboxes are already recorded, so it is contained), console auth, and a desktop surface behind the existing Surface interface — the seam was designed for it.
"What went wrong building it?"Lead with G2 being impossible and the suite still green. It is the strongest thing you can say: the system was tested against the real application, and that is the only reason it was found.
